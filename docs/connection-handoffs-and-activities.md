# Connection handoffs and Board Activities

> Historical implementation and verification record. OpenCode support was
> removed on 2026-10-08. Its references below describe saved history and
> earlier observations, not a supported creation or execution path.

NIM-2691 implements the new work-handoff policy on the existing execution-semantics-3 workflow and Run services. The saved policy marker is `definition.handoffs: { "contractVersion": 1 }`. It is distinct from the old optional `definition.repeat` contract. The two cannot coexist in one saved definition. Omission of both on an **old** saved version retains its ordinary DAG meaning; omission of `maxWorkHandoffsPerRun` on a **marked new** work connection means no per-connection cap.

## Saved work connections

The existing `execution` edge is the canonical work connection. It retains its ID, label, endpoints and graph presentation. Its optional `maxWorkHandoffsPerRun` is an integer from 1 through 2,147,483,647. Missing means unlimited for this connection, with no sentinel in JSON or SQL. `workRequestDirection` is `source_to_target` by default; `both` also permits independently initiated work in the reverse direction. A correlated return is allowed regardless of that setting because it returns the exact admitted request. The backend rejects a second edge for the same unordered node pair in a marked definition, including a reverse edge. The same connection ID and Run-wide counter apply to either permitted new-work direction. Approval relationships remain separate and never carry a work cap.

The marker changes execution meaning, so it is a meaningful staged Save, not a geometry edit. `workflow_validate_v3`, `workflow_save_v3`, `workflow_saved_get_v3` and the matching authenticated HTTP definition endpoints use the same shared `WorkflowDefinitionV3Schema`. The writer publishes a complete immutable definition/version with a new content hash and revision; the current Board draft and Operator MCP send the same fields. No direct edge PATCH is part of this contract. The saved version, not the currently edited Board, governs a Run.

## Work and quota identities

Every request, return, activation, native attempt, cap denial and notice has a different durable ID. All carry the exact workspace, workflow, Run and immutable version scope. Each activation also carries a root `lineageId`, preserved across sibling branches and correlated returns. An accepted new business work request has `requestId`, requester activation and execution, destination node, connection ID, accepted source-result digest and a 1-based ordinal. The logical request key includes both source execution and saved connection, so a finished turn can send work to two independent branches. Its accepted reservation charges one slot, including request #1. An ambiguous native submission is still charged until reconciled; technical retries never reserve a second slot. The counter key is `(run_id, workflow_version_id, relationship_id)`. A new Run starts at zero. Nodes can share several independently counted connections.

The return carries the originating `requestId`, exact requester and reviewer activations, accepted result digest, latest deliverable, remaining findings and `accepted | needs_changes`. It charges nothing. A native result uses typed `routing.kind: request | return | finish` and a named request outcome or exact return request ID. The server maps a named request outcome to a saved edge, checks live grants and capacity, and rejects an invented, forbidden or exhausted target. It never infers routing from prose. Permission and approval exchanges, progress, notices, replays, delivery acknowledgements and technical retries do not charge work slots. Independent reverse work on a `both` connection does.

An activation has its own ID and causal `entry | dependency | join | work_request | work_return | limit_denial` reference. A native attempt belongs to that activation, not merely `(run,node)`. When one requester activation fans out, its correlated returns share one continuation. It waits until every handoff has returned, finished, failed or stopped, then receives all returns and terminal failures together. Replaying a return cannot queue another continuation. If every reviewer accepts without remaining findings, their final exports release the saved outgoing `join: all` connections; mixed feedback starts rework without releasing a partial review round. Input bindings keep exact source activation, request, accepted result digest and destination activation. A multi-input `join: all` has one waiting activation keyed by Run, root lineage and destination; distinct incoming requests queue it once only when all required source results have arrived. Intermediate feedback cannot satisfy a downstream dependency; only an exact final accepted export can release an all-required join. The ordinary DAG still determines initial/dependent work. A later work request is admitted as a guarded transition in the **same** engine and Run; the old block occurrence and `blockForNode` are not its identity. There is no arbitrary graph-cycle admission.

| Trigger | Atomic durable transition | Native effect and next state |
| --- | --- | --- |
| New authorized work request, `used < limit` or unset limit | Lock Run/connection; deduplicate request ID and digest; reserve ordinal `used + 1`; publish request and activation intent | Existing owner/session/Stop fences control one destination launch. Reservation remains charged during uncertain delivery. |
| Identical request replay | Return the original receipt | No new activation, native turn or charge. Conflicting digest is rejected. |
| New work request with exhausted connection | Persist one denial and one requester continuation intent; count unchanged | Destination never launches. Requester receives a workflow-owned notice or remains explicitly delivery-unknown. |
| Correlated return with `accepted` | Persist return and result ancestry | Resolve the accepted path. No extra requester wake-up solely because the cap was reached. |
| Final allowed return with `needs_changes` | Persist return plus exhausted-destination notice in the **same** requester activation/continuation | Requester receives review feedback and notice once, and may choose another saved, authorized connection with capacity. |
| Return with remaining work and another slot available | Persist return and one requester continuation | Requester may revise and submit new work; that next request is the next charge. |
| No available authorized route | Persist `needs_direction` for the accepted work result; after independent branches settle, record a direction wait | The Run remains pending and waiting, with no forged approval or global Stop. User Stop remains available. |
| Stop or uncertain native delivery | Preserve admission, ownership, session and receipt evidence | No blind native resend or replacement session. Existing settlement/recovery determines a safe next action. |

The exhausted-destination notice text is: “The maximum number of work handoffs to agent C has been reached (3 of 3 for this Run). Choose another available agent or finish with the remaining findings.” `C` and the numbers are rendered from the pinned destination and durable usage. The continuation also contains the exact last deliverable, unresolved findings, causal request/return and server-validated alternatives. The third needs-changes review and notice share one logical wake-up. A later attempted fourth request has its own idempotent denial/notice and no C launch. Repeated automatic denial of the same decision is forbidden.

The notice outbox stores queued, pending, delivered and unknown separately. Binding B's workflow-owned native input makes delivery pending; only B's exact accepted native result acknowledges delivery. A recovered launch without an exact session changes pending to unknown and never gets another dispatch permit. If B repeats an already denied exhausted route in the same lineage, the accepted result becomes `run_work_unresolved` instead of creating another denial or wake-up. B can also finish with nonempty findings; that is unresolved work, not an approved result. Once other branches settle, `run_work_direction_waits` records the unresolved IDs and the Run transitions to `waiting/pending` through the existing graph publication. Normal authorized Stop settles it; restart recognizes the exact direction-wait record and does not resume a native turn.

## API and activity read contract

The existing authenticated definition save/read routes and Operator tools persist and read `handoffs`, `maxWorkHandoffsPerRun` and `workRequestDirection` through the common authoring service. NIM-2695 adds one authorized per-Run handoff projection and Activities read service:

* `GET /api/management/workspaces/:workspaceId/runs/:runId/handoffs` and Operator `run_handoffs_get_v1`: saved connection ID, pinned endpoints/names, nullable cap, Run-wide used count, named route availability, and exact unresolved/continuation state. This topology read requires both scoped `runs:read` and `workflows:read`; availability is rechecked at actual admission. A nullable cap in this **read** shape represents the absent saved field.
* `GET /api/management/workspaces/:workspaceId/runs/:runId/activities?cursor=<opaque>&limit=<bounded>` and Operator `run_activities_get_v1`: ascending durable sequence, stable logical ID, timestamp, exact Run/version/Agent/activation/connection references, public kind/severity/status/summary and bounded safe detail. An initial read returns the latest bounded page; `olderCursor` pages backward inside its frozen high-water, while `nextCursor` catches up forward. Both use the same live grant check. An invalid cross-Run cursor is rejected; an anchor outside the most recent 1000 public activity rows returns `ACTIVITIES_CURSOR_EXPIRED` (410) and requires an initial reload. The underlying `run_activity` audit is retained; only the public feed window is bounded.
* Work requests/returns are workflow-origin operations through the existing native/Run authority, not a management write endpoint or Agent-chat send. They require the saved route and the current Run grants. Read-only callers cannot acquire write authority from an Activities or quota read tool.

Activities is an append-only account of what happened, not a second execution-state store. Sequence, rather than timestamp, orders equal-time or out-of-order provider timestamps. UI catch-up deduplicates by stable logical ID and sequence, bounds retained pages, and clears private rows after confirmed access revocation. Display names come from the immutable saved workflow node, with a generic fallback when that name is unsafe to publish; mutable current Agent names are not substituted for a Run's pinned label. Pending approvals stay in the authorized approval inbox. `decided`, delivery pending/failed, native delivered and worker acknowledged are separate states. Draft validation/save warnings stay in Board notices.

Provider reasoning, raw prompts/tool arguments, credentials, unobserved log text, estimated progress and standalone Agent chat are not Activities facts. The SQL page projects named safe fields instead of transferring original JSON bodies. Missing provider detail is displayed as unavailable, never synthesized. The bounds query reads at most 1001 recent sequence IDs and the page query at most 101 rows through the existing `(run_id,sequence)` index; the PostgreSQL test checks the index and bounded `EXPLAIN` plans. Detailed accepted input/result and native evidence remain behind the existing authorized inspection reads.

## Migration and deployment

The NIM-2693 forward SQL migration creates `run_work_activations`, `run_work_results`, `run_work_connection_usage`, `run_work_requests`, `run_work_returns` and `run_work_denials`, plus activation-scoped native slot and attempt keys. NIM-2694 adds `run_work_notices`, `run_work_unresolved` and `run_work_direction_waits`. Neither migration updates historical `workflow_versions`, `runs`, repeat occurrences or accepted results. Deploy additive schema before admitting marked new Runs. Old in-flight Runs remain pinned to the old definition and existing recovery/Stop path. Old ordinary definitions without `repeat` do **not** acquire unlimited handoff semantics. Existing finite multi-node blocks are never inferred to be one pair. Conversion requires an explicit new authored definition, a new immutable version and a visible explanation of any unsupported mapping; the old version and its Runs stay readable. New workflow creation adopts the marker only when the new engine and UI are ready together.

A definitive cancellation before request admission leaves no counter row or charge. Once the accepted request and reservation commit, later cancellation or uncertain native delivery does not refund that ordinal or erase its ancestry. A new Run alone resets usage.

Run-wide `maxNodeExecutions`, owner/session/Stop gates and technical retry limits remain separate safeguards. Unlimited connection allowance removes only that connection's cap and never creates an automatic loop.

## FLOW-03 notice and direction qualification

`workNoticeMigration.ts` adds a per-cause notice outbox and immutable unresolved-work evidence. A notice's queued snapshot is frozen into the requester activation input; mutable delivery state is separate. `workHandoffAdmission.ts` commits a denied request, one B continuation and one notice together, or attaches the exhausted notice to the already-created third needs-changes return. The workflow-owned native prompt is built from that saved input. Repeated exhausted routing in the same lineage records `needs_direction` once, without another wake-up. After all branches settle, the Run enters a durable pending direction wait; an authorized Stop remains available.

The opt-in real Codex/OpenCode acceptance test has passed four boundary stories against task-owned PostgreSQL and the production app: review three returning needs-changes places the exact C notice in B's single return continuation and B selects D without a fourth attempt; an explicit fourth B→C decision is denied with no C launch, followed by one denial continuation and B→D; with no B alternative, A's independent D branch completes, B preserves the remaining finding, the Run waits for direction, reconcile makes no new native turn, and authorized Stop settles it; when C accepts review three, no notice or fourth B turn is created and the Run completes. Each case checks B–C usage 3, C executions 3, A executions 1 and exact request/return ancestry. The accepted-review case also reads the activity page through the production authenticated HTTP route. The PostgreSQL race test covers a last-slot race, two concurrent replays of one denial, Stop before B admission, Stop after notice binding, unknown delivery and frozen input replay.

## Board controls and Activities

New workflows have the explicit `handoffs` marker. Hovering, focusing or touching a work-connection pill opens a labeled editor for its finite limit or leaves it unset for no connection cap. Apply changes only the local draft; the established Save, Discard and protected Stop-and-save publication paths own persistence. Old unmarked saved definitions retain their existing semantics. A selected Run's line reads its immutable saved limit and separately displays the authenticated `/handoffs` usage. Approval connections have no work-limit pill. Both Board readbacks are independently scoped and authorized; a denied or mismatched response is withheld.

The Run drawer's Activities section reads the public `/activities` service. It starts only for the selected Run, keeps stable server sequence/ID order, catches up through frozen newer pages, deduplicates overlap, and bounds both service and client history to 1,000 public rows. A stale cursor or revoked read hides loaded rows until an explicit refresh. Older pages preserve scroll; new rows show an indicator when the reader is above the bottom. Agent/kind filters are linkable Board URL state and survive Run switches. The approval inbox remains the place to make pending decisions; draft warnings remain Board notices. Provider reasoning, prompts, raw tool arguments, secrets and unverified progress are absent from the public wire contract.
